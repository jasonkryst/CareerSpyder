# CareerSpyder application audit — 2026-08-19

A full-app review covering security, UI/UX, and accessibility, requested
as a standalone health check (not tied to a specific feature branch).
Scope: the whole running app (all routes/pages), plus the adapters,
config, and template code behind it, as of `v0.37.1`.

Methodology: a static code review of `app/` (routes, adapters, config,
templates, static JS/CSS) plus a live pass against a locally-run instance
(`uvicorn`, empty + partially-populated database) using a real browser —
screenshots, the accessibility tree, dark/light theme, and a mobile
(375px) viewport. `pip-audit` was run against the installed dependency
set. This was not a penetration test against a deployed instance, and it
does not cover load/performance testing.

Severity labels (Critical/High/Medium/Low/Informational) reflect impact
*within CareerSpyder's documented trust model*: a single-operator app
designed for a trusted home/private network with no authentication (see
[SECURITY.md](../../SECURITY.md)). Findings that only restate that
already-accepted posture are not repeated here as new issues.

## Summary

| Area | Critical | High | Medium | Low |
|---|---|---|---|---|
| Security | 0 | 1 | 3 | 3 |
| UI / UX / functional | 0 | 0 | 3 | 3 |
| Accessibility | 0 | 0 | 1 | 2 |

The codebase's baseline hygiene is good: clean `pip-audit`, intact Jinja2
autoescaping, correctly-escaped digest emails, ruff's bandit ("S") rules
enabled, non-root Docker runtime, and a deliberate, already-documented
no-auth trust boundary. The issues below are concrete gaps found on top
of that baseline, not a re-litigation of the trust model itself.

## Security

*(Full findings from a dedicated code-level security review; see
methodology above. File:line references are relative to the repo root.)*

### High

**H1. SSRF via user-supplied source URLs, reachable through
`/sources/test-preview` with no CSRF protection to gate it**
`app/web/routes_sources.py:112-126`, `app/config.py` (URL fields are
plain `str`, no scheme/host validation), `app/adapters/generic_html.py`,
`indeed.py`, `linkedin.py`, `infor.py`, `talentbrew.py`, `workday.py`,
`phenompeople.py`, `browser.py`

Every URL-bearing source field (`GenericHtmlSource.url`,
`LinkedInSource.url`, `IndeedSource.url`, `InforSource.url`,
`TalentBrewSource.base_url`, `WorkdaySource.career_site_url`,
`PhenomPeopleSource.career_site_url`, `FindlySource.career_site_url`) has
no scheme allow-list and no check against internal/link-local address
ranges. `POST /sources/test-preview` takes this straight from form data
and immediately executes the corresponding adapter server-side — no
source needs to be saved first. For `generic_html` with `render_js:
true`, `linkedin`, `indeed`, and `infor` (all of which drive Playwright's
Chromium via `browser.py`'s `page.goto(url, ...)`), this lets a request
make the server navigate to **any URL reachable from the container**,
including RFC1918 ranges, `localhost`, cloud metadata
(`169.254.169.254`), and `file://` paths — Chromium renders these even
though the plain `requests`-based adapters refuse `file://`. Combined
with `generic_html`'s attacker-supplied CSS selectors, this turns the
preview endpoint into an SSRF read-oracle for anything reachable from the
container's network namespace that also happens to render `<a href>`
elements (an internal admin UI, Portainer, another LAN service, etc.).

Because there is no CSRF protection at all (H1 is gated by M1), this is
exploitable as a drive-by pivot: an unrelated malicious webpage, visited
by anyone whose browser can reach the CareerSpyder instance, can trigger
this blind — the attacker never needs direct network access to the
instance themselves. That exceeds the documented trust model, which
assumes the attacker is *on* the trusted network, not that they can
reach it through a LAN user's browser.

*Fix:* validate URL fields with `pydantic.AnyHttpUrl` restricted to
`http`/`https`; resolve the hostname and reject loopback/link-local/
RFC1918 targets (re-checked after redirects) before both `requests` calls
and `page.goto()`; restrict `browser.py`'s Playwright navigation to
`http(s)` only. Prioritize alongside M1, which is what makes this
remotely triggerable.

### Medium

**M1. No CSRF protection on any state-changing route**
All ten `@router.post(...)` handlers across `routes_dashboard.py`,
`routes_jobs.py`, `routes_settings.py`, `routes_sources.py`

No anti-CSRF token, `Origin`, or `Referer` check exists anywhere. The app
sets no cookies/sessions, so this isn't classic session-riding CSRF, but
the mechanics are the same: any page a trusted-network user's browser
visits can auto-submit a plain `application/x-www-form-urlencoded` POST
directly to the app, and the server processes it purely by network path.
Concrete chains: silently add an attacker address to `email_to` via
`/settings/preferences` then trigger `/run-now` so future digests get
BCC'd out; add a malicious `generic_html`/`linkedin`/`indeed` source
pointed at an internal URL (chains into H1); wipe job-dedup state via
`/settings/data/clear-cache`; drive `/sources/test-preview` blind.

*Fix:* since there's no session to carry a per-user token, reject
state-changing requests whose `Origin`/`Sec-Fetch-Site` doesn't match the
app's own host, or require a custom header on POSTs issued via the app's
own `fetch()` calls — a simple cross-site form POST can't set custom
headers without a CORS preflight, which fails closed here (no
`CORSMiddleware`).

**M2. Unbounded file upload on settings import**
`app/web/routes_settings.py:178-192`, `app/config.py:123-127`

`UploadFile.read()` has no size cap before the bytes are `json.loads()`'d
and validated. Starlette spools large uploads to a temp file rather than
holding them fully in memory, but there's still no upper bound on upload
size or JSON parse cost before validation. Lower real-world exploitability
than H1/M1 since a file input can't be driven cross-site without user
interaction.

*Fix:* enforce an explicit max content-length before/while reading rather
than an unbounded `upload.read()`.

**M3. No concurrency/rate limit on Playwright-driven preview fetches**
`app/web/routes_sources.py:112-126`, `app/adapters/browser.py`

Each `render_js` preview launches a fresh headless Chromium instance with
no limit on concurrent invocations, unlike `orchestrator.run_once`, which
is serialized by `_run_lock`. Repeated/parallel requests (reachable via
M1) can spawn many simultaneous Chromium processes and exhaust host
CPU/memory — a straightforward DoS, and worse than the existing
scheduled-run cost because it's on-demand per request.

*Fix:* add an in-process semaphore/lock around preview fetches, mirroring
`orchestrator.py`'s `_run_lock`.

### Low

**L1. `board_token` interpolated unescaped into fixed-host API URLs**
`app/adapters/greenhouse.py:9`, `app/adapters/lever.py:9` — validated
only as `min_length=1`, placed directly into the URL path with no
`urllib.parse.quote`. Host is fixed, so not SSRF, but a token containing
`/`, `?`, or `#` could redirect to an unintended path or inject query
params on that host. Low impact (operator-configured value), but M1
weakens the "self-configured" assumption.
*Fix:* `urllib.parse.quote(source.board_token, safe="")`, or restrict the
field to `^[A-Za-z0-9_-]+$` at the pydantic level.

**L2. Unhandled `ValueError` on malformed `max_pages`**
`app/web/source_form.py:72,80,85,97` — `int(form["max_pages"])` isn't
guarded; a non-numeric value raises a bare `ValueError` before the
pydantic model is even constructed, producing an unhandled 500 instead of
the graceful re-render other validation failures get.
*Fix:* wrap the conversions or pre-validate with a regex.

**L3. Loose dependency version floors, no ceilings**
`pyproject.toml:8-16` — all runtime deps are `>=` only. `pip-audit` is
currently clean, so this is hygiene rather than an active issue, but an
unpinned ceiling means a future major bump (e.g. Starlette changing
autoescape defaults) could land unreviewed.
*Fix:* consider a lockfile or upper bounds on security-sensitive deps
reviewed on a cadence.

### Informational (verified, no gap found)

- Digest email HTML escaping is correct: every interpolated field goes
  through `html.escape`, and hrefs go through `safe_url_scheme`
  (`app/textutils.py:29-37`), which neutralizes non-`http(s)` schemes
  including obfuscated `javascript:`-style payloads.
- Jinja2 autoescaping is intact everywhere — no `| safe` or
  `{% autoescape false %}` in any template.
- The documented `app/db.py` S608 ruff-ignore holds up: every dynamic SQL
  clause draws only from fixed allow-list dicts or a literal ASC/DESC
  ternary; all real values go through `?` placeholders.
- No secrets appear in any log call site.
- `SMTP_PASSWORD` is correctly absent from the settings export payload.
- Docker hardening is solid: digest-pinned base image, non-root uid 1000
  via `setpriv` after a root-only `chown`, no secrets baked into the
  image.

## UI / UX and functional

**U1 (Medium — real bug). "None" leaks into the Company field after a
validation error**
`app/web/source_form.py`'s `echo_source()` (`company=form.get("company")
or None`) combined with `source_form.html`'s
`{{ source.company if source else '' }}`: since the echoed object itself
is truthy, Jinja renders `source.company`, which is the Python object
`None` — printed as the literal text **"None"** in the input's value.
Reproduced live: submitting Add Source with Company left blank re-renders
the form with `None` visibly typed into the Company box. The same `x or
None` echo pattern is used for `selectors.location`, so it likely has the
same bug there too.
*Fix:* render `{{ source.company or '' }}` (and the same for
`selectors.location`), or have `echo_source` keep the raw submitted
string instead of coercing falsy values to `None`.

**U2 (Medium — UX/robustness). Raw framework/library exceptions are
shown directly to the end user**
`app/web/routes_sources.py:70,98` render pydantic's raw
`ValidationError` text (e.g. *"1 validation error for GreenhouseSource
board_token String should have at least 1 character
[type=string_too_short, input_value='', input_type=str] For further
information visit https://errors.pydantic.dev/2.13/v/string_too_short"*)
directly into the form's `.error` div. `routes_sources.py:118,125`
(`/sources/test-preview`) goes further and returns `str(exc)` for
**any** exception the adapter raises — Playwright, `requests`, or
BeautifulSoup internals included — verbatim as the JSON `error` field.
This is confusing, non-actionable jargon for the app's actual audience
(a self-hosting home user), and a minor incidental information leak of
internal model names, library versions, and adapter internals.
*Fix:* catch `ValidationError` and map field errors to short, human
phrasings ("Board token is required") instead of `str(exc)`; for the
preview endpoint, log the full exception server-side and return a
generic "Couldn't fetch this source: <adapter-appropriate summary>"
instead of the raw exception text.

**U3 (Medium — UX consistency). "Clear job cache" has no confirmation,
unlike every other destructive action**
`app/web/templates/settings_data.html:15-16` — "Delete" (source,
`sources_list.html:41-43`) and "Import settings"
(`settings_data.html:24-25`) both use the app's `data-confirm-*` modal
before submitting. "Clear job cache," on the same page, does not, despite
its own adjacent copy warning it "may send a large digest email" as a
side effect. This is the one destructive action on the page a user can
trigger with a single accidental click.
*Fix:* add the same `data-confirm-title`/`data-confirm-message`
attributes used elsewhere on this page.

**U4 (Low). Ambiguous "Status" naming on the Jobs page**
`app/web/templates/jobs.html:30,44,68` — the filter bar has two
different fields: one labeled **"Status"** (filters Active/Removed
lifecycle) and one labeled **"Job status"** (filters
Applied/Ignored/Accepted/Rejected/Not Interested). The *table column*
also labeled **"Status"** shows the second concept, not the first — so a
user filtering by "Status" expecting it to match the "Status" column
gets the wrong filter. Same "Status" = Active/Removed naming repeats
consistently on `/jobs/map`, so it isn't a typo, just a collision with
the column name.
*Fix:* rename the Active/Removed filter to something like "Listing
status" or "Active/Removed," freeing "Status" to mean the same thing in
the filter and the column.

**U5 (Low). No client-side or visual indication of required fields**
`app/web/templates/source_form.html` — none of the per-type-required
inputs (Name, Board token, URL, etc.) carry `required`/`aria-required`,
and there's no visual marker (asterisk or similar). The only feedback is
the server-side pydantic error after a failed submit (see U2). Given the
form conditionally shows/hides fields by source type, a blanket
`required` attribute isn't a trivial drop-in, but at minimum the visibly
active fields for the selected type could be marked.
*Fix:* toggle `required` alongside the existing `showFieldsFor()`
visibility logic in `source_form.html`'s inline script, and consider a
lightweight required-field indicator.

**U6 (Low). Destructive-action confirmation has no non-JS fallback**
`app/web/static/confirm-modal.js` — the confirm dialog is pure
client-side; if JS fails to load or is blocked, any
`data-confirm-message` form (Delete source, Import settings) submits
immediately with **zero** warning rather than falling back to a native
`confirm()` or a safe default. The rest of the app is designed to
degrade to plain full-page-reload behavior without a JS build step, but
this one interaction loses its safety net entirely instead of failing
safe.
*Fix:* wrap the submit-time confirmation in a `window.confirm()` fallback
when `<dialog>`/`showModal` isn't available, or accept the trade-off
explicitly and note it in `AGENTS.md`.

## Accessibility

The foundation here is genuinely solid and worth calling out before the
gaps: a skip-to-content link, correct `banner`/`navigation`/`main`/
`contentinfo` landmarks, `aria-current="page"` on the active nav link,
`fieldset`/`legend` grouping on every settings form, a visible
`:focus-visible` outline using the theme's accent color, a native
`<dialog>` for the confirm modal (built-in focus trap + Escape-to-cancel
via the browser), a mobile nav toggle with correct `aria-expanded`,
Escape-to-close, and click-outside handling, and a responsive
table→stacked-card pattern (`data-label` + CSS) that keeps data readable
on narrow viewports without losing table semantics on wide ones. Spot-
checked text/background color pairs in both themes (body text, muted
footer text, accent links/buttons) all clear WCAG AA contrast.

**A1 (Medium — WCAG 3.2.2 "On Input"). Per-job Status select auto-submits
with no visible trigger**
`app/web/templates/jobs.html:86` — the per-row Job Status `<select>` on
`/jobs` has `onchange="this.form.submit()"` and no visible Save/submit
button. Changing the selection triggers an immediate full-page
navigation. This is a recognized accessibility anti-pattern: it changes
context from a mere input change, with no warning, which is disorienting
for keyboard and screen-reader users in particular (arrowing through
options to explore them can commit and submit before the user has
decided), and it also costs every user their scroll position on a
possibly long, filtered table.
*Fix:* submit via `fetch()`/`requestSubmit()` against a small AJAX
handler that patches just the row (consistent with the app's existing
`toast`/live-region patterns), or add a visible per-row "Save" control.

**A2 (Low). `/jobs/map`'s Leaflet container has no accessible name**
`app/web/templates/jobs_map.html:45` — `<div id="map" ...>` has no
`aria-label` or `role`. A screen-reader user landmark-scanning the page
gets an unlabeled region with no indication of its purpose. The "Table
view" link is a reasonable escape hatch (and the map is inherently
visual), but the container itself should still be identifiable.
*Fix:* add `aria-label="Job locations map"` (or similar) to the map
`div`.

**A3 (Low). Form validation errors aren't announced as an alert**
`app/web/templates/source_form.html:4` (`{% if error %}<div
class="error">{{ error }}</div>{% endif %}`) — the error banner has no
`role="alert"`/`aria-live`. Because this is a full page reload (not an
AJAX injection), the practical impact is small — the error sits right
below the `<h1>` — but marking it explicitly would guarantee it's
announced regardless of where focus lands after the reload.
*Fix:* add `role="alert"` to the `.error` div in `source_form.html` (and
the equivalent in the settings templates, which follow the same
pattern).

## Recommended priority order

1. **H1 + M1** together — the SSRF surface is only remotely triggerable
   because there's no CSRF gate; fixing M1 first meaningfully shrinks
   H1's blast radius even before URL validation lands.
2. **U1** — a one-line template fix for a visibly broken form field.
3. **U3** — a one-line template attribute addition, matching an existing
   pattern already used twice on the same page.
4. **A1** — the auto-submitting select is the clearest accessibility
   anti-pattern found and has a straightforward fix.
5. Everything else, roughly in the severity order above.

No Critical-severity findings were identified.
