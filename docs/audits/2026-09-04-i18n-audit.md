# i18n/l10n Audit — 2026-09-04

## Scope and methodology

This audit examined CareerSpyder (FastAPI + Jinja2, self-hosted, single-operator
job-search assistant — see `README.md` and `SECURITY.md`) for internationalization
and localization readiness. It covers:

- Hardcoded user-facing English strings (templates, routes, flash messages,
  email digest, JS toasts).
- Date/time formatting and timezone handling.
- Number/currency formatting.
- Character-encoding handling for non-English scraped data (job titles,
  company names, locations) and for hand-edited config files.
- `<html lang>` and RTL layout considerations.
- A pragmatic recommendation on whether full UI translation is worth pursuing.

Method: manual read-through of `app/*.py`, `app/adapters/*.py`, `app/web/*.py`,
`app/web/templates/*.html`, and the two static JS files that touch dates
(`dates.js`), plus `README.md`/`SECURITY.md` for intended audience. This is a
read-only audit — no code was changed.

**Framing up front:** CareerSpyder is explicitly a single-operator, self-hosted
tool (`SECURITY.md`: "CareerSpyder v1 is explicitly designed for a trusted
home/private network," no auth, no multi-tenant story). There is one person
using one UI language at a time — themselves. That context should drive the
recommendation more than a generic i18n checklist would: translating the UI
is a cost with no realistic payoff here, whereas mishandling non-English
*data* (job titles, company names scraped from real career sites worldwide)
is a correctness bug that hurts the single operator directly, regardless of
what UI language they read.

## Summary of current state

- **No i18n framework is wired up.** No `gettext`, `babel`, `_()` markers, or
  equivalent. Confirmed by grep across `app/` — zero hits.
- All ~214 template text nodes across 14 templates, all flash messages (10
  call sites via `app/web/flash.py`), all JS toast strings, and the entire
  email digest (`app/digest.py`) are hardcoded English string literals.
- `app/web/templates/base.html:2` hardcodes `<html lang="en">`. No RTL
  (`dir="rtl"`) support anywhere in templates or `style.css`.
- Backend date/time handling is timezone-*aware* and mostly well-built
  (`datetime.now(UTC)` used consistently in `db.py`, `checker.py`,
  `geocoding/service.py`, `scheduler.py`), and the web UI already
  auto-localizes displayed timestamps client-side via `Intl.DateTimeFormat`
  in `app/web/static/dates.js`. This is good practice already in place —
  not a gap.
- No currency/salary fields exist anywhere in the schema, adapters, or
  templates, so there is no currency-formatting surface to audit.
- Scraped-data adapters mostly go through `resp.json()` (encoding-safe per
  the JSON spec) or a real browser engine (Playwright, also encoding-safe).
  One adapter (`generic_html`) does not, and that's a real bug (see below).

## Findings — Correctness risk (non-English *data* handling)

These affect correctness even though the UI stays English-only. Severity
reflects "risk of silently mangling or crashing on real non-English input,"
not "how far from full i18n we are."

### 1. `generic_html` adapter decodes HTML with the wrong fallback encoding — **Medium**

`app/adapters/generic_html.py:15-19`:

```python
resp = http_get(source.url, timeout=15)
resp.raise_for_status()
html = resp.text
...
soup = BeautifulSoup(html, "html.parser")
```

`requests` derives `resp.encoding` from the `Content-Type` response header;
per RFC 2616 it falls back to **ISO-8859-1 (Latin-1)** for any `text/*`
content-type that omits an explicit `charset=`. Many real-world careers
pages (this adapter exists specifically for arbitrary third-party career
pages configured via `source_form.html`) serve UTF-8 without declaring a
charset. When that happens, `.text` decodes valid UTF-8 bytes as Latin-1,
producing classic mojibake (e.g., "Zürich" → "ZÃ¼rich") in job titles,
company names, and locations that then get persisted to the database and
mailed out in the digest — silently, with no error.

BeautifulSoup ships its own `UnicodeDammit` encoding sniffer that does a
much better job than requests' RFC-mandated Latin-1 fallback, but only if
given raw bytes.

**Fix:** pass `resp.content` (bytes) to `BeautifulSoup(...)` instead of
`resp.text`, and let bs4's own encoding detection run:

```python
html = resp.content
...
soup = BeautifulSoup(html, "html.parser")  # bs4 sniffs encoding from bytes
```

(Note: `linkedin.py` and `indeed.py` use `render_html()`/Playwright, and all
of `workday.py`, `phenompeople.py`, `greenhouse.py`, `healthcaresource.py`,
`findly.py`, `lever.py`, `talentbrew.py` use `resp.json()` — both paths are
encoding-safe already and need no change.)

### 2. `config.py` reads/writes `sources.json` without an explicit encoding — **Medium**

`app/config.py:120-121` and `app/config.py:131-132`:

```python
def load_sources(path: str) -> list[SourceConfig]:
    if not os.path.exists(path):
        return []
    with open(path) as f:
        data = json.load(f)
    ...

def save_sources(path: str, sources: list) -> None:
    ...
    with open(tmp_path, "w") as f:
        json.dump(payload, f, indent=2)
    os.replace(tmp_path, path)
```

Neither `open()` call passes `encoding="utf-8"`. Python's default text
encoding is `locale.getpreferredencoding(False)` — on Windows this is
typically a codepage like cp1252, and on a minimal Linux container with no
locale configured it can be `ascii`/`ANSI_X3.4-1968`. The README explicitly
documents hand-editing `sources.json` as a supported workflow ("You
maintain the list of sources through a small web UI... or by hand-editing a
JSON file"). A user who hand-edits the file with a non-ASCII company label,
saved as UTF-8 by their editor (the near-universal default today), will hit
a `UnicodeDecodeError` on the next `load_sources()` call in a non-UTF-8
locale/container — an outright crash, not just mangled text.

The write side (`save_sources`) is not actually at risk today only by
accident: `json.dump(..., indent=2)` defaults to `ensure_ascii=True`, so it
always emits pure-ASCII output (`\uXXXX`-escaping anything non-ASCII)
regardless of the file handle's encoding. That's not a correctness bug, but
it does mean round-tripped `sources.json` files become unreadable
`\uXXXX`-escaped noise for anyone who put a real accented company name in,
which fights the "hand-editable JSON" design goal.

**Fix:** add `encoding="utf-8"` to both `open()` calls; optionally add
`ensure_ascii=False` to the `json.dump` call in `save_sources` (line 132)
so hand-edited non-ASCII content stays human-readable on export/save.

```python
with open(path, encoding="utf-8") as f:
    data = json.load(f)
...
with open(tmp_path, "w", encoding="utf-8") as f:
    json.dump(payload, f, indent=2, ensure_ascii=False)
```

(`import_sources_json` in `config.py:142-144` and the settings
import/export handlers in `app/web/routes_settings.py:168-204` are fine —
they operate on `bytes`/`str` via `UploadFile.read()` and Starlette's
`Response`, both of which are UTF-8-safe by default and don't go through a
locale-dependent `open()`.)

## Findings — Informational (UI-language only)

These are real gaps against a "full i18n" checklist, but they carry no
correctness risk for a single English-reading operator. Recommend **Low /
Won't Fix** given the single-user context (see Recommendation below).

- **No i18n framework** — no `gettext`/Babel/`_()` wiring anywhere in `app/`.
- **~214 hardcoded template strings** across 14 files in
  `app/web/templates/` (largest: `jobs.html` at 489 lines, `guide.html` at
  172 lines of instructional prose, `source_form.html` at 175 lines).
- **10 hardcoded flash messages** via `app/web/flash.py`, e.g.
  `app/web/routes_jobs.py:196` (`"Job marked as removed."`),
  `app/web/routes_settings.py:64` (`"Email settings saved."`),
  `app/web/routes_sources.py:74` (`"Source added."`).
- **Hardcoded JS toast strings** in `app/web/templates/jobs.html` (e.g. line
  283, `"Failed to update status."`; line 377, `"Failed to update duplicate
  flag."`).
- **Digest email is entirely hardcoded English** — `app/digest.py:32-35`
  builds the subject line (`f"CareerSpyder: {len(new_jobs)} {job_label}(s)"`
  / `"CareerSpyder: run had failed sources"`), and the body headings
  (`"Sources that failed this run"`, `"View all jobs"`) are literal strings
  throughout `build_digest()`.
- **`<html lang="en">` hardcoded**, `app/web/templates/base.html:2`; no
  `dir="rtl"` handling and no logical-property (`margin-inline-start` vs
  `margin-left`) usage in CSS — irrelevant unless a translated UI is ever
  built.
- **Digest timestamp uses a fixed English/US format** —
  `app/digest.py:39`: `searched_at.strftime('%b %d, %Y %I:%M %p %Z')`
  produces month abbreviations and 12-hour AM/PM in English regardless of
  operator locale (Python's `strftime` here runs in the process's default
  "C" locale since nothing calls `locale.setlocale()`, so this is at least
  *consistent* — never mangled, just always English/US-formatted). Contrast
  this with the web UI's `dates.js`, which correctly uses
  `Intl.DateTimeFormat(undefined, ...)` to render every `<time>` element in
  the *viewer's* browser locale and local timezone — the email digest is the
  one place that doesn't get this treatment, because it's rendered
  server-side with no "viewer" to localize for.
- **English day-of-week codes** (`mon`..`sun`) as the internal
  `email_days` representation (`app/scheduler.py:13`,
  `app/web/templates/settings_preferences.html`) — implementation detail,
  fine as-is.

## Non-findings (checked, no issue)

- **Timezone correctness (backend):** consistent, correct use of
  timezone-aware UTC (`datetime.now(UTC)`) throughout `db.py`,
  `checker.py`, `geocoding/service.py`, and `scheduler.py`; the scheduler
  correctly resolves an operator-configured IANA `tz` string
  (`app/scheduler.py:16-19`, `app/web/main.py:24`) via `zoneinfo` for cron
  scheduling. No naive-datetime bugs found.
- **Timezone/locale correctness (frontend):** `app/web/static/dates.js`
  already does this right — renders all `<time datetime="...">` elements
  using `Intl.DateTimeFormat(undefined, {...})`, which automatically uses
  the viewer's browser locale and local timezone. This is the correct
  pattern and should be the model for fixing the digest email (Finding
  above), not something the digest needs to reinvent — email just can't use
  browser APIs, so it needs an explicit operator-timezone parameter instead.
- **Currency/salary/number formatting:** no such fields exist anywhere in
  `app/models.py`, the adapters, or the templates. Nothing to audit, nothing
  to fix.
- **JSON-API adapters' encoding:** `workday.py`, `phenompeople.py`,
  `greenhouse.py`, `healthcaresource.py`, `findly.py`, `lever.py`, and
  `talentbrew.py` all call `resp.json()`, which auto-detects UTF-8/16/32 per
  the JSON RFC independent of HTTP headers — safe for non-Latin company
  names, job titles, and locations.
- **Playwright-rendered adapters' encoding:** `indeed.py` and `linkedin.py`
  get HTML via `page.content()` from a real Chromium instance
  (`app/adapters/browser.py`), which decodes exactly as a browser would —
  safe.
- **`app/textutils.py` text normalization:** `to_summary()` uses
  `BeautifulSoup(...).get_text()` and Unicode-aware `\s+` regex collapsing —
  does not assume ASCII, does not mangle non-Latin scripts.
- **SQLite storage:** Python's `sqlite3` module stores/retrieves `TEXT`
  columns as Unicode `str` transparently (UTF-8 on disk) — no
  encoding-related risk found in `app/db.py`.
- **HTML charset declaration:** `app/web/templates/base.html:4` correctly
  declares `<meta charset="utf-8">`.
- **Settings export/import (`routes_settings.py`):** operates on
  `bytes`/`UploadFile`/Starlette `Response`, all UTF-8-safe by construction
  — no encoding risk despite not touching `config.py`'s buggy `open()`
  calls.

## Recommendation

**Do not invest in full UI translation.** This is a single-operator,
unauthenticated, home-network tool by design (`SECURITY.md`). There is no
multi-user, multi-locale audience to serve, no product reason to add a
translation framework, string-extraction tooling, or a language switcher,
and doing so would be pure cost — more surface area to maintain, more places
for the operator's *own* future changes to introduce bugs — for zero
realistic benefit. The ~214 template strings, 10 flash messages, and the
digest email can all stay hardcoded English indefinitely. Mark all
"Informational" findings above **Won't Fix**.

**Do fix the 2 correctness issues, they're cheap and real:**

1. `app/adapters/generic_html.py:17` — pass `resp.content` (bytes) to
   `BeautifulSoup` instead of `resp.text`, so bs4's own encoding sniffer
   runs instead of requests' Latin-1 fallback. One-line change; prevents
   silently mangled company/job names for any `generic_html` source (the
   adapter explicitly built for arbitrary third-party sites) whose server
   doesn't declare a charset.
2. `app/config.py:120` and `app/config.py:131` — add
   `encoding="utf-8"` to both `open()` calls (and optionally
   `ensure_ascii=False` to the `json.dump` on line 132). One-line-each
   change; prevents a crash or silent mangling the moment the operator
   hand-edits `sources.json` with a non-ASCII company name on a non-UTF-8
   locale — a workflow the README explicitly documents as supported.

Optional, lower priority: give the digest email
(`app/digest.py:39`) an operator-configurable timezone for its
`searched_at` timestamp, mirroring what `dates.js` already does for the web
UI, so the "Searched ..." line in the email reflects the operator's local
time instead of always UTC. This is a nice-to-have, not a correctness bug —
the timestamp is accurate and unambiguous (UTC, `%Z` prints "UTC"), just not
localized to the reader.

**Net effort:** the two correctness fixes above are each a 1-line diff. Fix
those; leave everything else as-is.
