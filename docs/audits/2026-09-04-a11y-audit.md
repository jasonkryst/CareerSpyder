# CareerSpyder accessibility audit — 2026-09-04

A focused accessibility (a11y) re-audit of the current templates and
static assets, following up on the Accessibility section of
[2026-08-19-app-audit.md](2026-08-19-app-audit.md) (v0.37.1, 1 Medium +
2 Low found). Scope: every Jinja2 template in `app/web/templates/`
(`base.html`, `dashboard.html`, `jobs.html`, `jobs_map.html`,
`settings_data.html`, `settings_email.html`, `settings_preferences.html`,
`settings_tabs.html`, `source_form.html`, `sources_list.html`,
`guide.html`, and the `_external_link.html` / `_history_rows.html` /
`_sort_header.html` partials) plus every static JS/CSS file that drives
their interactive behavior (`confirm-modal.js`, `dashboard.js`,
`dates.js`, `map.js`, `leaflet_renderer.js`, `nav.js`, `preferences.js`,
`theme.js`, `toast.js`, `style.css`).

**Methodology: static-only.** `chrome-devtools-mcp` and the `playwright`
MCP server both failed to connect in this environment (connection
timeouts), and no `mcp__claude-in-chrome__*` browser-automation tools
were available either, so no live browser pass, screen-reader tree
inspection, or rendered-contrast measurement was possible this round.
Everything below comes from reading the Jinja2 source, the JS that
mutates the DOM at runtime, and manual WCAG 2.x contrast-ratio
calculations against the literal hex values in `style.css`'s
`:root` / `[data-theme]` / `prefers-color-scheme` blocks (light and dark
both checked). Rendered-focus-order, actual screen-reader announcement
behavior, and true on-screen contrast (which can shift with
subpixel/AA font rendering) should still be spot-checked live before
treating the contrast findings below as final — the arithmetic is
correct for the source colors, but a live pass is the only way to
confirm what assistive tech actually announces for the modal-labeling
finding (H1).

## High

### H1. The shared confirm-modal has no accessible name or description, on every destructive action in the app

`app/web/templates/base.html:76-83`

```html
<dialog id="confirm-modal" class="modal">
  <h2 id="confirm-modal-title">Please confirm</h2>
  <p id="confirm-modal-message"></p>
  ...
```

This single `<dialog>` backs every `data-confirm-*` form in the app —
"Delete source" (`sources_list.html:41-45`), "Clear job cache"
(`settings_data.html:15-19`), and "Import settings" — i.e. every
irreversible action available. Both the title (`h2#confirm-modal-title`)
and the message (`p#confirm-modal-message`, populated per-action by
`confirm-modal.js:23-24` with e.g. `Delete "Acme Corp — Backend
Engineer"? This can't be undone.`) already have `id`s, but the `<dialog>`
itself carries neither `aria-labelledby` nor `aria-describedby`. When
`showModal()` runs, focus lands on the Cancel button
(`base.html:80`) with no name/description wired to the dialog — a
screen-reader user hears only "Cancel, button" and has no way to know
*what* they're being asked to confirm before choosing Confirm or Cancel.
Compare this to `jobs.html`'s two purpose-built dialogs
(`duplicate-modal` at `jobs.html:173`, `location-override-modal` at
`jobs.html:193`), which both already correctly set
`aria-labelledby="...-title"` — so the fix pattern already exists
elsewhere in the codebase, it just wasn't applied to the one dialog that
gates every delete/overwrite action.

*Fix:* add `aria-labelledby="confirm-modal-title"
aria-describedby="confirm-modal-message"` to the `<dialog>` tag in
`base.html:76`.

## Medium

### M1. Row-action icon buttons fail color contrast in their resting (non-hover) state

`app/web/static/style.css:608-618` (`.icon-btn`), used by the duplicate
button (`jobs.html:111-116`), location-override button
(`jobs.html:121-126`), and "mark removed" button (`jobs.html:132-135`)

```css
.icon-btn {
  color: var(--fg-muted);
  opacity: 0.6;
  ...
}
.icon-btn:hover {
  opacity: 1;
  color: var(--accent);
}
```

`--fg-muted` (light theme `#5c5c5f`) already sits at a comfortable
6.65:1 against `--bg` (`#ffffff`) on its own, but `opacity: 0.6` blends
it toward the page background before contrast is measured, dropping the
*effective* rendered color to roughly `rgb(157,157,159)` — a **2.71:1**
contrast ratio against white. That fails both the 4.5:1 text minimum
(SC 1.4.3) and the 3:1 non-text/UI-component minimum (SC 1.4.11) that
would apply if these are treated as icons rather than text. The dark
theme is better but still fails: `--fg-muted` (`#a8a6a5`) at 0.6 opacity
on `--bg` (`#0d0d0e`) works out to roughly **3.56:1** — clears the 3:1
UI-component bar but still misses 4.5:1. A low-vision user in light mode
gets a resting-state glyph with meaningfully-below-AA contrast for the
only three interactive controls in the Jobs table besides the row link
itself; the improved contrast only appears on hover, which isn't
available to touch or keyboard users at all before activation.

*Fix:* drop the resting-state `opacity: 0.6` (or raise it enough that
`--fg-muted` still clears 4.5:1 after blending — roughly 0.85+ opacity
in light mode) and rely on the existing `:hover`/`:focus-visible` state
for the "de-emphasized until interacted with" visual effect instead of
baking it into the default contrast.

### M2. The same icon buttons also fall below the minimum touch/click target size

`app/web/static/style.css:608-618` (`.icon-btn`)

```css
.icon-btn {
  padding: 0 var(--space-1);   /* 0 vertical padding */
  font-size: 1rem;
  line-height: 1;
  ...
}
```

With zero vertical padding and `line-height: 1` at a 16px font size, the
clickable box for the duplicate/location-override/remove buttons is
roughly 16px tall by ~20-24px wide — well under the WCAG 2.2 SC 2.5.8
"Target Size (Minimum)" bar of 24×24 CSS px, and much further under the
24-44px range generally recommended for mobile taps. These buttons sit
inline in a data table that, per the app's own responsive design, is the
*primary* layout on a 375px mobile viewport (`style.css:456-510`), so
this is exactly where it matters most — a mobile/motor-impaired user
trying to tap the 📍/🔂/🗑 icons next to a job row has a genuinely small
target to hit, immediately next to other tappable content (the job title
link, badges).

*Fix:* give `.icon-btn` explicit `min-width`/`min-height: 24px` (ideally
closer to 32-44px) with `display: inline-flex; align-items: center;
justify-content: center;` so the padding box — not just the glyph —
meets the minimum, without needing to enlarge the visible icon.

### M3. Every page in the app shares one identical, non-descriptive `<title>`

`app/web/templates/base.html:6`

```html
<title>CareerSpyder</title>
```

There is no `{% block title %}` anywhere — Dashboard, Jobs, Sources, all
three Settings tabs, and the Guide all render the exact same
`<title>CareerSpyder</title>`. This is present (not empty), so it isn't
a hard SC 2.4.2 "Page Titled" failure in the strictest sense, but it
fails the intent of that criterion: a screen-reader user switching
browser tabs, a low-vision user scanning a long tab list, or anyone using
browser history/bookmarks gets zero information about which of the six
pages they're on from the title alone — everything reads "CareerSpyder."
This is a systemic, one-line-per-template fix that touches the entire
app.

*Fix:* add `{% block title %}{% endblock %}` inside `<title>{% block
title %}CareerSpyder{% endblock %}</title>` in `base.html:6`, then
override it per template, e.g. `{% block title %}Jobs — CareerSpyder{%
endblock %}` in `jobs.html`, `Sources — CareerSpyder` in
`sources_list.html`, `Settings: Email — CareerSpyder` in
`settings_email.html`, etc.

### M4. Repeated per-row actions share one generic accessible name with no way to distinguish rows

`app/web/templates/sources_list.html:39` (Edit links), `:41-45` (Delete
buttons); `app/web/templates/settings_preferences.html:54,61` (Remove
buttons for each recipient row)

```html
<td data-label="Edit"><a href="/sources/{{ s.id }}/edit">Edit</a></td>
...
<button type="submit">Delete</button>
```

Every row in the Sources table renders an `<a>` whose entire accessible
name is the literal word "Edit," and every row's delete `<form>` renders
a `<button>` whose accessible name is just "Delete" — with N sources
configured, a screen-reader user pulling up a links/buttons list (a
common navigation pattern in NVDA/JAWS/VoiceOver) sees "Edit, Edit, Edit
… Delete, Delete, Delete" with no way to tell which source each one acts
on without first navigating into the table to find surrounding context.
`settings_preferences.html`'s recipient rows have the same "Remove,
Remove, Remove" pattern, though with a much smaller/finite list so it's
lower-impact. This is exactly the pattern the app *does* get right
elsewhere — `jobs.html:116,126,134` all set
`aria-label="... for {{ job.title }}"` on their icon buttons — it just
wasn't carried over to the Sources page or the Recipients list.

*Fix:* add `aria-label="Edit {{ s.name }}"` to the Edit link
(`sources_list.html:39`) and `aria-label="Delete {{ s.name }}"` to the
Delete button (`sources_list.html:44`); for
`settings_preferences.html:54,61`, either accept the lower-severity
version as-is (small, adjacent list) or add
`aria-label="Remove recipient"` plus a live-region announcement of which
email was removed, matching `preferences.js`'s existing
focus-management care (`preferences.js:24`).

### M5. Full-page error banners still aren't announced as alerts (2026-08-19 A3 — still open, wider than originally scoped)

`app/web/templates/source_form.html:4`,
`app/web/templates/settings_data.html:6-8`,
`app/web/templates/settings_preferences.html:6-8`

```html
{% if error %}<div class="error">{{ error }}</div>{% endif %}
```

The 2026-08-19 audit flagged this exact pattern in `source_form.html`
and predicted "the equivalent in the settings templates, which follow
the same pattern" — confirmed still present, unchanged, in both
`settings_data.html` and `settings_preferences.html` as well. None of
the three carry `role="alert"`. Since these are full page reloads (not
AJAX), impact is still real but partial (the error sits right under the
`<h1>`, so a screen-reader user reading top-to-bottom will still
encounter it) — but nothing guarantees it's announced if focus/reading
position lands elsewhere after the reload, and it costs nothing to fix.
By contrast, `jobs.html:204`'s dynamically-shown `.modal-error` div
*does* already carry `role="alert"` — so, similar to H1/M4, the fix
pattern is already established elsewhere in the same codebase.

*Fix:* add `role="alert"` to all three `.error` divs listed above.

### M6. "Test this source" results and errors update the DOM with no live-region announcement

`app/web/templates/source_form.html:79` (`#test-results-error`,
`#test-results-wrap`), JS at `:109-129`

```html
<div id="test-results-error" class="error" hidden></div>
<div id="test-results-wrap" class="table-scroll" hidden>
```

Clicking "Test this source" (`source_form.html:78`) fires an async
`fetch()` to `/sources/test-preview` (which, per the prior audit's H1,
can itself be a slow Playwright-driven request) and then either unhides
`#test-results-error` with an error message or unhides
`#test-results-wrap` with a results table — but neither container has
`role="alert"`/`aria-live`, and there's no "Testing…" status announced
while the fetch is in flight. A screen-reader user clicking the button
gets total silence until they manually re-explore the page to discover
whether it succeeded, failed, or is still running — worse than the
equivalent flow in `jobs.html`, which uses `toast()` /
`aria-live="polite"` regions (`toast.js:20-36`,
`dashboard.html:11,13`) for every other async action in the app.

*Fix:* add `role="alert"` to `#test-results-error`
(`source_form.html:79`), add an `aria-live="polite"` status span next to
the "Test this source" button that's set to "Testing source…" on click
and "Found N jobs" / cleared on completion (mirroring the
`run-now-status`/`history-status` pattern already used in
`dashboard.html:11,13` + `dashboard.js:52,56`).

## Low

### L1. `jobs.html`'s two custom dialogs label the title but not the subtitle

`app/web/templates/jobs.html:173-211`

`duplicate-modal` and `location-override-modal` both correctly set
`aria-labelledby="...-title"`, but neither sets `aria-describedby` to
point at the adjacent `<p id="duplicate-modal-job">` /
`<p id="override-modal-job">` subtitle (e.g. "Software Engineer —
Acme Corp"), so that context is available visually but not guaranteed to
be read as part of the dialog's accessible description.

*Fix:* add `aria-describedby="duplicate-modal-job"` /
`aria-describedby="override-modal-job"` alongside the existing
`aria-labelledby` on both `<dialog>` tags.

### L2. Map popup job links skip the "opens in new tab" cue used everywhere else in the app

`app/web/static/leaflet_renderer.js:35-36`

```js
return "<li>" + badge + "<a href=\"" + url + "\" target=\"_blank\" rel=\"noopener noreferrer\">"
  + title + "</a> — " + company + "</li>";
```

Every other external link in the app goes through the
`external_link()` macro (`_external_link.html:1-3`), which appends a
visible ↗ glyph plus `<span class="sr-only"> (opens in new tab)</span>`.
The Leaflet popup HTML is built by hand in JS and skips that entirely —
job links inside map marker popups open in a new tab with no warning,
inconsistent with the rest of the app's (good) pattern.

*Fix:* append the same `sr-only` "(opens in new tab)" span (and ideally
the ↗ glyph) to the generated `<a>` in `popupHtml()`.

### L3. Contextual badges convey their meaning only through a mouse-only `title` tooltip

`app/web/templates/jobs.html:106,110,119,127,364(js),436(js)`

```html
{% if job.is_secondary %}<span class="badge badge-secondary" title="Secondary source">2°</span>{% endif %}
...
<span class="location-overridden-badge" title="Location manually overridden">&#9998;</span>
```

The "2°" secondary-source badge and the "✎" location-override badge both
rely on a `title` attribute for their full meaning; `title` tooltips only
appear on mouse hover (nothing on touchscreens, nothing via keyboard).
The "Duplicate" badge's own extra detail ("Marked as duplicate of X") has
the same problem (`jobs.html:110`, and the JS that updates it at
`jobs.html:364`). A keyboard-only or touchscreen user sees the bare glyph
with no way to reveal what it means beyond what the character itself
suggests.

*Fix:* add `aria-label` (or replace `title` with visible adjacent text
in a `.sr-only` span) carrying the same content, e.g. `aria-label="{{
'Marked as duplicate of ' + job.duplicate_of if job.duplicate_of else
'Marked as duplicate' }}"` alongside the existing `title`.

### L4. `#toast-container`'s fixed-position CSS rule never applies (id/class selector mismatch)

`app/web/templates/base.html:68` vs. `app/web/static/style.css:530`

```html
<div id="toast-container" aria-live="polite" aria-atomic="true">
```
```css
.toast-container {
  position: fixed;
  top: var(--space-4);
  right: var(--space-4);
  ...
}
```

The element uses `id="toast-container"`; the CSS rule targets
`.toast-container` (a class). No element in the app carries that class
(confirmed via repo-wide search), so this rule never matches — toasts
render in normal document flow, right after `</footer>`, rather than as
a fixed top-right overlay. This is primarily a functional CSS bug, but
it has an accessibility angle worth flagging: a sighted, non-AT user
relying on the toast's expected fixed position to notice a
save/delete/status confirmation may miss it entirely if it's rendered
off-screen in the document flow instead (screen-reader users are
unaffected, since the `aria-live="polite"` announcement itself still
fires regardless of visual position).

*Fix:* change `.toast-container` to `#toast-container` in
`style.css:530` (one-character fix).

### L5. `badge-duplicate` text contrast is marginally under AA for its size/weight

`app/web/static/style.css:648-652`, `:5` (`--fg-muted`)

```css
.badge-duplicate {
  background: var(--fg-muted);
  color: #fff;
  opacity: 0.8;
}
```

White text on `--fg-muted` (`#5c5c5f`) blended at 0.8 opacity toward the
light-theme page background works out to roughly **4.11:1** — just under
the 4.5:1 AA minimum for normal text, and the badge text (0.75rem,
weight 600) doesn't meet the "large text" exemption threshold (needs
≥18.66px bold). This is a small miss, not a stark failure, but is
concretely below AA as specified.

*Fix:* drop the `opacity: 0.8` (or compensate by darkening
`--fg-muted` slightly) so the rendered background clears 4.5:1 against
white text.

### L6. Guide's "Web UI tour" table has no `<thead>`/`<tbody>`

`app/web/templates/guide.html:24-50`

```html
<table>
  <tr><th scope="col">Page</th><th scope="col">Purpose</th></tr>
  <tr><td>...
```

`scope="col"` is present so the header cells are still correctly
identified, but the header row sits directly under `<table>` with no
`<thead>`, and the data rows have no `<tbody>` — every other table in the
app (`_history_rows.html`, `jobs.html`, `sources_list.html`,
`source_form.html`'s test-results table) uses proper `<thead>`/`<tbody>`
sectioning. Low practical impact given `scope="col"` already does the
heavy lifting, but worth fixing for consistency and because some
AT/browser table-navigation shortcuts (e.g. "jump to next data row")
rely on `<tbody>` boundaries.

*Fix:* wrap the header `<tr>` in `<thead>` and the remaining rows in
`<tbody>`, matching every other table in the app.

### L7. Sort-direction glyphs aren't marked decorative, duplicating what `aria-sort` already conveys

`app/web/templates/_sort_header.html:4`

```html
<th scope="col"{% if active %} aria-sort="{{ 'descending' if desc else 'ascending' }}"{% endif %}>
  <a href="...">{{ label }}{% if active %} {{ '▼' if desc else '▲' }}{% endif %}</a>
</th>
```

The column header already correctly sets `aria-sort` on the `<th>`
(a real strength — most apps skip this). The visible ▼/▲ glyph inside the
link text is redundant with that and, unmarked, gets read literally by
some screen readers (e.g. "black down-pointing triangle") appended to
the link name — mildly noisy rather than actively wrong, since
`aria-sort` is already the authoritative signal.

*Fix:* wrap the glyph in `<span aria-hidden="true">{{ '▼' if desc else
'▲' }}</span>` so only `aria-sort` communicates direction to AT.

### L8. `/jobs/map`'s `#map` container labels itself with `aria-label` but no `role`, which some screen readers won't reliably expose

`app/web/templates/jobs_map.html:63`

```html
<div id="map" aria-label="Job locations map" data-jobs-url="..." style="height: 600px;"></div>
```

This is the 2026-08-19 A2 fix (see below) and is a real improvement, but
a bare `<div>` with only `aria-label` and no explicit `role` isn't
guaranteed to be exposed as a distinct named object by every
screen-reader/browser combination — landmark and "named region" behavior
generally expects a role (`region`, `img`, `application`, etc.) alongside
the label. Low severity since the page already provides the "Table view"
link as a full non-visual escape hatch.

*Fix:* add `role="img"` (the map is effectively a static, non-editable
graphic once loaded; Leaflet's own pan/zoom controls have their own
native button semantics) or `role="region"` alongside the existing
`aria-label`, whichever better matches intended screen-reader behavior
after a live check.

## Informational

### I1. Toast notifications auto-dismiss after 5 seconds with no pause on hover/focus

`app/web/static/toast.js:5,34`

Both the server-rendered flash toast and the JS-created
`showToast()` toasts self-remove via a flat `setTimeout(..., 5000)` with
no pause-on-hover/focus and no way to request more time — relevant to
WCAG SC 2.2.1 "Timing Adjustable," though the impact here is soft since
the toast is purely informational (a status echo of an action the user
just took, not new information required to proceed) and a manual
`.toast-close` button is always available. Worth a low-cost improvement
(clear the timer on `mouseenter`/`focusin`, restart on `mouseleave`/
`focusout`) rather than a hard requirement.

## Recommended priority order

1. **H1** — one-line fix (`aria-labelledby`/`aria-describedby` on the
   shared confirm dialog), and it's the highest-traffic dialog in the
   app: every delete/overwrite action in CareerSpyder routes through it.
2. **M5** — also a near-trivial fix (`role="alert"` ×3), and directly
   closes out the one still-open finding from the prior audit.
3. **M1 + M2** — both are the same `.icon-btn` CSS rule; fixing contrast
   and tap-target size together is one small, self-contained change.
4. **M3** — `{% block title %}` touches every template but each edit is
   one line; worth batching as a single pass.
5. **M4 + M6** — apply the `aria-label`/live-region patterns the app
   already uses correctly elsewhere (`jobs.html`) to the two places that
   were missed (Sources list, source-test-preview).
6. Everything under Low/Informational, roughly in listed order — none
   are urgent, but L1-L3 and L5 are all one-attribute-or-line fixes.

No Critical-severity findings were identified — nothing in this app
fully blocks a screen-reader or keyboard-only user from completing a
task, though H1 comes closest for the specific case of confirming a
destructive action blind.
